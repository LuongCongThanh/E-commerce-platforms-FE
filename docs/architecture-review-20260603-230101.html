1. Collapse the HTTP client pipeline

Strong in-process
src/shared/lib/http/api-client.ts src/shared/lib/http/client.ts src/shared/lib/http/api-types.ts

Before

http.get<T>(url) caller
apiGet() / api-client.ts pass-through
httpClient.request() / client.ts pass-through
axios (interceptors buried here)

3 layers. Auth injection & error transform hidden in axios interceptors. Callers exposed to URL + method + schema.

After

http.get<T>(url) caller
http module auth injection · retry · error transform · axios

One seam. Auth & error logic visible in one file. Delete api-client.ts.

Problem

Three-layer delegation — interface nearly as complex as implementation. Auth token injection and error normalisation buried in axios interceptors, invisible to callers.

Solution

Collapse api-client.ts into client.ts. One deep module owns the full request lifecycle. Delete the pass-through wrapper.

Wins

  • Locality: auth & error logic concentrate in one module
  • Interface shrinks; implementation absorbs the wrappers
  • Delete one file, zero callers change
  • Leverage: one test suite covers all HTTP behaviour

3. Consolidate the product query engine

Strong in-process
src/app/[locale]/(shop)/_lib/hooks/useProducts.ts src/app/[locale]/(shop)/_lib/hooks/useSearch.ts src/app/[locale]/(shop)/_lib/hooks/useHomeData.ts src/shared/hooks/useProductFilters.ts

Before — filtering logic triplicated

useProducts — interface
filter + sort + paginate (impl)
useSearch — interface
filter + sort + paginate (impl)
useHomeData — interface
static passthrough

Filtering rules duplicated × 3. Change sort → touch 3 files.

After — one deep product query module

useProducts(query) — single interface
filter engine sort logic pagination search by query home / featured

Locality: filtering changes in one module.

Problem

Filter, sort, and pagination logic duplicated across 3+ hooks. Shallow modules with nearly identical implementations. Adding a filter (e.g. stock availability) requires touching every hook.

Solution

One useProducts(query) interface taking a unified query object. Filter engine is internal. Browse, search, and home pages all cross one seam.

Wins

  • Locality: filter logic in one module — fix once, fixed everywhere
  • Leverage: interface shrinks from 3 hooks to 1
  • Delete useSearch.ts and useHomeData.ts as separate modules
  • Interface is the test surface — test filtering without mounting components

Wins

  • Interface is the test surface — test pricing without a router
  • Validation schema reusable for server action
  • Component shrinks to pure UI; no hidden redirect

Strong deletion test

Before — re-export layer adds no depth

Deletion test: delete shared/base/. Complexity moves to callers (update imports). Module was not earning its keep.

After — import directly, or own the variants

Feature Component
shadcn directly

OR: if a wrapper earns its keep (adds CVA variants, project-wide defaults), keep it — but make it deep.

Button (deep) CVA variants · size defaults · icon support

Problem

33-file module that re-exports shadcn primitives. Interface is as complex as implementation (it is the implementation). Deletion test: deleting adds no real complexity — just import-path updates.

Solution

Delete the pass-through re-exports. Keep wrappers that add actual depth (variants, project-specific defaults). Import shadcn directly everywhere else.

Wins

  • Delete 20–30 shallow wrappers in one move
  • Locality: any real variant logic lives in one deep module per component
  • Interface shrinks to what actually varies
  • No false sense of design-system enforcement from hollow re-exports

6. Resolve Product type duplication

Worth exploring in-process
src/shared/types/product.ts src/app/[locale]/(shop)/_lib/types/product.ts src/app/[locale]/(shop)/_lib/data/products.ts 
flowchart LR

  classDef leak stroke:#dc2626,stroke-width:2px;

Two Product type definitions. If the API schema changes, which gets updated? The shared one is the source of truth — the local one leaks implementation details (mock data shape) into the type layer. Solution: delete local type, extend shared Product if feature needs extra fields (use z.extend()).

Wins

  • Locality: one source of truth for Product shape
  • API schema changes propagate once
  • Leverage: shared Zod schema validates at every entry point

Top recommendation

Start with #3 — Product query engine

Three hooks doing nearly identical filter-sort-paginate work. This is the highest-leverage deepening: collapsing them concentrates all query logic in one module with a single, testable interface. The deletion test is decisive — deleting any one hook forces duplication into the remaining two. Fix that first.

#1 (HTTP client collapse) and #2 (auth module) are almost as strong but require more careful seam design. #5 (delete base-component pass-throughs) is a quick win with zero design risk.
